Veent WiFi Portal — monorepo

Three apps, two packages, one router seam

A captive-portal business: guests buy WiFi time through a MikroTik hotspot, staff run operations through an admin dashboard. Everything that touches the router passes through a single interface.

Boundaries

System architecture

Five bounded regions. The customer app is the only one a guest reaches; the admin app is the only one that provisions the router; @veent/db is the sole schema authority for all three apps.

The seam that matters

Every router call goes through NetworkController (packages/core/src/integrations/network/types.ts:150). Six core services import it; two factories implement it — createMikrotikController and createStubNetworkController. Swapping to the stub for tests changes one env var, not a single call site.

Constraints

Rules the architecture depends on

  • Return URL The post-payment browser return uses event.url.origin, driven by ORIGIN — which in production must be the guest-reachable, walled-gardened LAN address. The guest device is still captive at redirect time. TUNNEL_ORIGIN is for the server-to-server webhook only.
  • Auth split Two isolated betterAuth() instances — customer (veent-portal) and admin (radius-admin) — each with its own secret and schema builder. They are never cross-wired.
  • MAC trust resolveMacForUser returns { mac, live }. A fallback-resolved MAC is not a verified binding and must not drive auto-bind or entrench last_known_mac.
  • AP binding resolveNetworkIdForMac resolves the Option-82 circuit-id first, so a session on a shared hotspot bridge binds to the physical AP row rather than the bridge.
  • Walled garden Three tagged groups — probe, payment, portal — plus a scheduler-maintained gcash-auto IP row. Default setup:router is purely additive; --reconcile prunes only code-owned allow rows.
  • Cycle One import cycle exists: IssueForm.svelte → sentry/index.ts → SentryKpis.svelte → feature/index.ts → IssueForm.svelte.
